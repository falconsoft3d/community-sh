1. Concepts and permissions

  • Project: groups instances and containers (usually one per customer). It has a colour, tags (to filter in «Projects») and, optionally, a client and «Test mode» for demos.
  • Quotas (set only by administrators, when editing the project): maximum instances and reserved RAM (the sum of its instances' memory limits). Checked when creating, duplicating, moving, creating from a backup, requesting a demo and raising a memory limit. Metrics → Usage by project shows what each one takes against its quota (also as CSV, for billing) and on the 1st of every month the summary arrives by email.
  • Instance: an Odoo (versions 8 to 20) with its own PostgreSQL, filestore, network and address. Shown as project / instance.
  • Task: anything that takes time (deploy, back up, restore, duplicate, install modules, clean up…) is run by a background worker, one at a time, with its log and progress bar (see Tasks and Activity).

Who can do what

  • Administrator (superuser): everything, including Users, Docker, the global Settings (domain, backups, AI, email, demos) and the Docker cleanup.
  • User: creates and manages their projects and instances.
  • Client (the user's «Client» checkbox, assigned to a project): sees their projects and does what the project allows in Client permissions (when editing it): deploy, restart and stop; create and download backups; see the logs (all three yes by default); restore their backups and log into Odoo as admin (no by default). Never changes code or configuration, doesn't see the Master Password or the administrator's password, nor the Console, Domains, Modules and Migrate tabs. Everything they do is recorded in the audit log. The same rules apply in the API and MCP.

2. Create an instance

  1. Dashboard or Project → New instance.
  2. Choose the project, name, Odoo version and, if you have your own code, the GitHub repository (HTTPS) and branch. Private repositories need your token in Settings → GitHub.
  3. Optional: database name (empty = auto-detect), «Default database for demos» (several databases in one instance, Odoo 18+) and a custom domain.
  4. On saving, a branch named after the instance is created in your repository (if there is a token) and the deploy is queued.

What the deploy does

  • Clones or updates the main repository and the extra repositories, pulls the Odoo image (old versions are emulated on ARM servers) and the PostgreSQL that matches the version.
  • Creates the odoo_<name> and db_<name> containers, their network and data volume, writes odoo.conf (Master Password, proxy_mode) and publishes the route in Traefik.
  • The instance is served at https://client-version-name.yourdomain with its Let's Encrypt certificate.
  • When it succeeds, an automatic Docker cleanup is queued.

Other ways to create an instance

  • Duplicate an instance: copies the database, filestore, repositories and environment variables. By default the copy is neutralized before it starts: incoming and outgoing mail, scheduled actions (except the automatic cleanup), payment methods and API keys switched off and a new database UUID (Odoo 16+ shows the «neutralized» ribbon). Untick «Neutralize the copy» (or send neutralize: false through the API) only if the copy will replace the original.
  • Refresh a staging copy: in the copy's Backups tab, «Refresh data from another instance» replaces its databases and attachments with those of another of the same version (by default, its original) without touching its code, branch or configuration, and neutralizes it (recommended). You type its name to confirm; it's recorded in the audit log.
  • From a backup: Backups → «Import a backup and create an instance» (detects the version and the database).
  • Through the API or MCP: creating an instance also deploys it (see API and MCP).
  • Demos from «Test mode» (see Demos).

The Odoo database isn't created automatically: create it in the instance page (Information → Create database: name, language and demo data) or through the API (create-database); both store the administrator's login and password. In new instances Odoo's manager (/web/database/manager) is closed; open it in Information only when you need it.

3. Manage an instance

The instance page has the tabs Information, Logs, Console, Domains, Modules, Backups, Migrate, AI and Recent tasks.

  • Deploy: deploys again (recreates the containers with the current configuration; data is kept).
  • Restart / Stop: restarting first starts the database if it was stopped. A stopped instance loses its Traefik route (no certificates spent) and gets it back when restarted. After a server reboot, instances come back on their own except the ones you stopped.
  • Rename (moves containers and volumes), Move to another of your projects (the address doesn't change) and Delete (removes containers, volumes, workspace, routes and its backups).
  • Memory limit (Information, 1536 MB by default): RAM cap of the Odoo container so one instance can't leave the server and the others without memory. Applied live, without a restart (the worker checks it every minute); 0 = no limit, on the next deploy. If Odoo reaches it, the system kills the process and Docker starts it again: raise it if an instance keeps restarting on its own.
  • Memory saving (Information, off unless you choose it): «Stop if nobody logs in for N days» (3, 7, 14 or 30; it reads its Odoo's login log, alerts the day before and when it stops it) and a daily schedule in UTC to start and stop it. Meant for test instances.
  • Description (demos): text shown next to the instance on its project's demo page.
  • Odoo Logs and a Console to run commands in the container.

4. Odoo access: admin and passwords

  • Log in as admin (key icon, on the instance page, the instance list and the project): opens Odoo as administrator without a password through a signed, single-use link valid for 60 seconds. On Odoo 10 and 11 it logs in with a panel-owned user («Administrador (Community SH)»).
  • Master Password: the one for the Odoo database manager (/web/database/manager). Shown and copied in Information; applied on redeploy.
  • Odoo database manager (Information): closed by default in new instances (existing ones stay open until you close it). Closed, /web/database/* and the XML-RPC db service answer 403 on its domains right away and, after a redeploy, Odoo also refuses to create, copy, download, restore or drop databases (list_db = False), on the direct port too. With several databases, log in with ?db=name. Opening or closing it is in the Audit log.
  • Administrator (Information): login and password of the Odoo administrator, with buttons to show and copy them, to share them. Shown when the platform set the password (database created through the API/MCP, demos, copies).
  • Reset password (in the Administrator block): gives the administrator a new password (the one you type, 8-64 letters, digits, «_» or «-», or a random one if left empty) in the instance's database, or in all of them if it has no fixed one, and stores it on the page. Also works when the database was created outside the platform. The old one stops working and its sessions are closed. The instance must be deployed. Also through the API (POST /api/instances/{id}/reset-admin-password/) and MCP (reset_admin_password), which return the password right away; the MCP's get_instance shows the administrator to who manages the instance.

If you change the administrator's password inside Odoo, the one shown in the panel no longer works: reset it from the panel to have it again.

5. Code, modules and configuration (Modules tab)

  • Extra repositories (OCA, odoo/enterprise…): HTTPS URL and branch; cloned and added to the addons_path on the next deploy. Private ones use the owner's GitHub token.
  • Pull: fetches the latest commits of the main and extra repositories and restarts Odoo, without redeploying.
  • Automatic update (on by default, «Pull and restart Odoo»; also «Pull and update all modules (-u all)» or Off):
    • A push to the branch of any of its repositories updates every running instance that uses that repository and branch (one webhook per repository is enough). «Create webhook on GitHub» button, or a URL and secret to add it by hand.
    • Also, every day from 02:00 UTC the worker pulls all of them. Odoo is only restarted (or -u all run) if a commit or the configuration changed.
  • Install a module by its technical name (or «Install the Community SH theme») in every database, optionally updating it (-u). If it fails, the database stays as it was.
  • Install from requirements.txt: pip installs the packages in the data volume, so they survive redeploys.
  • Environment variables of the Odoo container (NAME=value, one per line): applied on every deploy; only their names are shown. Copies inherit them; demos don't.
  • Browser (WhatsApp Web): installs Google Chrome in the Odoo container and reinstalls it on every deploy.

6. Domains and HTTPS (Domains tab)

  • Each instance has its subdomain client-version-name.yourdomain, covered by a single DNS record *.yourdomain. Traefik issues and renews the certificates.
  • Custom domain: point its DNS (A record) to the server's IP and set it in the tab; it can't take the subdomain of another instance or container.
  • If the certificate is missing, the page warns and explains why (DNS not pointing here, Let's Encrypt limit…). Let's Encrypt allows 50 certificates a week per domain.
  • The panel's main domain is set in Settings → Domain & SSL.

7. Backups and restores

  • Create backup (Backups tab): database and, optionally, filestore. With several databases, one copy of each is kept.
  • Automatic backups: Settings → Respaldos (on/off, frequency and how many copies to keep per instance). If any fails, an alert is sent.
  • Copy off the server (S3): in Settings → Respaldos, with an S3-compatible bucket (AWS S3, Backblaze B2, Cloudflare R2, Wasabi, MinIO…), every backup is also uploaded there as its own task («Copiar backup fuera (S3)»), is marked ☁ S3, and copies older than the given days are deleted from the bucket. «Probar conexión» checks that it can write, without saving anything. To recover one: in the instance's Backups tab, Copies in S3 → Show copies → Restore (downloaded and restored as a task).
  • Backup check: every week (or with «Comprobar backups ahora» in Settings → Respaldos) the latest backup of each instance is checked: the ZIP is intact, it holds a valid PostgreSQL dump and the S3 copy has the same size. If something fails, an alert is sent.
  • The panel itself: with the bucket configured, every day the task «Copia del panel fuera (S3)» uploads to _panel/ a copy of the panel's database (projects, users, settings…) and of the certificates (acme.json). The .env is deliberately not uploaded: it holds the key that decrypts the secrets; keep it elsewhere (e.g. a password manager), because without it a copy of the database can't recover the keys.
  • Restore a backup over the instance (Odoo is stopped and its connections closed before the database is recreated) or «Restore from a file».
  • Import: besides the panel's own backups, it accepts Odoo manager backups (.zip with dump.sql and filestore) and .dump files.
  • Backups menu: every backup, download, and «Import a backup and create an instance».

8. Demos (Test mode)

  1. In the project, tick Test mode: demo page URL (e.g. /bim), trial days (15), sibling project where demos are created, text for the visitor and demos at a time.
  2. The visitor opens the public page, picks a version among the project's running instances (with their description), leaves their details and solves the captcha.
  3. A copy is created in the sibling project, neutralized before it starts (its scheduled actions keep running): no outgoing mail, no API keys, unknown passwords for the other users and a new password for the administrator. The page shows the progress and then the address, login and password, which are also emailed if SMTP is set up.
  4. When it expires it is stopped, and deleted 7 days later.
  • Limits: one demo per email a month, 3 a month per connection, a daily maximum and a maximum of demos at a time on the server (Settings → Demos). It isn't created if memory is short.
  • Your website can request demos without a captcha with the project's API key («Test mode» card → Generate key).
  • Whoever requests a demo goes into Contacts, in the «Demo» stage.

9. Contacts (CRM)

  • One contact per email, with their details, their demos and your notes; kept even if the demo is deleted.
  • Kanban board: Contacted, Demo, Proposal, Waiting, Won and Lost (drag the cards). Also a list view, search, filters, manual entry and CSV export.

10. AI and migrations

  • AI assistant (AI tab, with AI set up in Settings → IA): creates and changes modules in the instance's addons and installs them. Accepts attachments and tagging modules with @, shows a step-by-step plan, and every answer that changed files has «Undo these changes».
  • /ia from Odoo: write /ia … in the chatter of any record and the answer arrives in that chatter.
  • Migrate (Migrate tab): brings data from another Odoo 8+ over XML-RPC into 14+ instances (contacts, products, sales, purchases, invoices and payments); can be repeated without duplicating.

11. Containers (apps)

  • Containers menu or Project → «New container»: apps from templates (e.g. ERPSqlite) or built from a repository and a Dockerfile.
  • Builds run in their own worker (they don't slow down deploys or backups). Each container gets https://name.yourdomain; when stopped it has no route.

12. Docker and disk cleanup

  • Automatic cleanup: every time an instance is created successfully (form, API/MCP, duplicate, from backup or demo), a cleanup of what Docker doesn't use is queued: stopped containers that belong to no instance, untagged and unused images, build cache and unused networks. Only one is queued even if several instances are created in a row; it's skipped while a container is being built.
  • «Clean up» button on the Dashboard (administrators): runs that same cleanup whenever you want.
  • Docker → Cleanup: shows what and how much is freed and lets you choose; unused volumes are only removed here, by typing BORRAR.
  • The panel, instances (even stopped ones), their filestores, databases and networks, and the panel's containers and volumes are never touched. A removed image is pulled again on the next deploy that needs it.
  • The logs of every container (Odoo, PostgreSQL, apps and the panel itself) are capped at 20 MB × 3 files, so a looping error can't fill the disk. Containers that already existed get it when they're recreated (on redeploy).
  • The server has limited memory: stop test instances when you're done.

13. Tasks and Activity

  • Every task keeps its full timestamped log and a live progress bar, in the instance's «Recent tasks» tab and in the Activity menu (filters by status, kind and instance).
  • Statuses: Queued, Running, Done and Failed (with the error). If the worker restarts mid-task, the task is marked as failed.

Availability and alerts

  • Every 5 minutes the worker requests the login page of each running instance (except those with a task in progress). After two failures in a row it marks it as Not responding (in the list and in Information, with the reason); when it answers, the response time is shown.
  • Alerts (Settings → General): when a task fails, an instance stops responding or comes back, the disk goes over 90 %, memory stays over 90 % for 5 minutes or an instance has no HTTPS certificate (checked hourly). They go by email to the «Emails para notificaciones» (or to the administrators) through the server in Settings → Email, and optionally to a webhook (Slack, Discord, Google Chat, n8n…). The same alert isn't repeated within 6 hours (24 for certificates).

14. Dashboard, Metrics and Todo

  • Dashboard: the main figures, each linked to its page; CPU, memory and disk in green (<50 %), orange (50-90 %) or red (>90 %). Clicking CPU, Memory or Disk opens the usage by instance sorted by that resource: which instance uses what.
  • Metrics: CPU and RAM usage over the last 24 hours, 7 days, 30 days and 12 months. Under Resources, usage by instance: CPU and RAM of its Odoo and PostgreSQL now (with how much of its limit it uses) and the disk of its data (database and attachments), code and backups, stopped instances included; sorted by clicking the headers. The disk is measured every 10 minutes or with «Measure the disk now». Below, usage by container.
  • On each instance page, Information shows its current usage (CPU and RAM of Odoo and PostgreSQL).
  • Todo: the team's tasks (to do, in progress, done) with a note of what was done.

15. API and MCP (Claude)

  • REST API (Settings → API → Generate token; Authorization: Bearer …): projects, instances (create and deploy, restart, stop, backup, duplicate, environment variables, extra repositories, create-database, install-module), backups, tasks with their log, containers, contacts, Todo and demos.
  • For an AI: Settings → API → «Generar token y descargar .md» creates a new token and downloads community-sh-api.md with the token, the base URL and the whole documentation (endpoints, tasks, errors, examples and, if enabled, how to connect MCP). Give it to Claude, ChatGPT… so it uses the API for you. Keep it like a password; the token is revoked in «Tus tokens».
  • MCP (Settings → MCP): connect Claude to /mcp/ with a personal token; it acts with its user's permissions.
  • Tokens are shown only once and require 2FA when it's mandatory.
  • Passwords given to a task (create a database, reset the administrator's) are never returned when reading tasks (shown as ••••••) and are removed from the task when it ends; the administrator's stays on the instance page.

16. Users, security and settings

  • Users (administrators): create, edit and mark as Client.
  • Audit log (administrators, in the menu): who did what and from which IP: sign-ins (failed ones too), every time someone shows or copies the Master Password or the administrator's password, «Log in as admin», password resets, settings changes, tokens created and revoked, users and instance changes (delete, rename, move, memory, environment variables). Passwords are no longer inside the page: they're requested from the server when you click show or copy.
  • Encrypted secrets: the GitHub token, the OpenAI key, the SMTP password, the S3 secret key and, for each instance, the Master Password, the administrator's password, the webhook secret and the environment variables are stored encrypted in the database; a copy of the database alone doesn't reveal them. The key is FIELD_ENCRYPTION_KEY in .env or, without it, one derived from DJANGO_SECRET_KEY: don't change either without decrypting first, or those values can no longer be read.
  • 2FA from your profile; turning it off or changing it asks for a current code. Access is locked after several failed attempts.
  • Settings: GitHub (token for private repos; its Help tab explains how to create it), Domain & SSL, General, Respaldos, IA, Email (SMTP with «Send test»), Demos, MCP and API.

17. Server security

  • Filtered Docker for the web: the panel's web container no longer has the Docker socket (which amounts to root on the server). It talks to Docker through the docker-proxy service, which lets through what the panel does (logs, console and pip, start, stop and restart, the Docker page, creating app containers) and refuses what would give the server away: privileged containers, extra capabilities or host namespaces, mounting host folders outside instances/, the Docker socket, entering, copying files from or removing the panel's own containers, its volumes and its internal network. Deploys, backups and other tasks still run in the workers.
  • An app container that needs another host folder (administrators only): add it to DOCKER_PROXY_ALLOWED_BINDS in .env (comma separated) and redeploy. Mounting the Docker socket (e.g. Portainer) is no longer possible from the web.
  • Read-only code: the web container mounts the code without write access (it only writes to media, backups, instances, letsencrypt, traefik, staticfiles and ai_attachments), so a bug in a page can't change the code the workers run. SQLite installs keep it writable (PANEL_CODE_MOUNT=rw).
  • Odoo database manager: closed by default (see Odoo access); a leaked Master Password isn't enough to download or drop the database from the internet.
  • No third-party scripts: Alpine.js, Lucide, Tailwind and Chart.js are served by the panel itself (static/vendor, pinned versions checked against npm), not from CDNs. A compromised CDN can't run code in the panel with your session.
  • Content-Security-Policy: the browser only runs the panel's scripts, only talks to the panel (it can't send data elsewhere), loads no plugins and won't put the panel in an iframe. Google Fonts and HTTPS images are still allowed.
  • Port 8000: with a domain the panel is only served through Traefik (HTTPS). The deploy adds PANEL_BIND=127.0.0.1 to .env when missing, so plain-HTTP port 8000 isn't open to the internet.

18. Panel updates

  • Every change to the panel bumps the version and is documented in About and in this Help.
  • A push to the main branch runs the tests on GitHub Actions (on PostgreSQL 16, the same engine as production) and, if they pass, deploys to the server: it waits for running tasks, saves a copy of the panel's database, frees space if less than 5 GB is left, builds and, once started, opens the main pages as an administrator (manage.py smoke_check). If the build fails, the panel doesn't answer or a page fails, it goes back to the previous version.
