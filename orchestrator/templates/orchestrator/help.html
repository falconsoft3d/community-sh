1. Conceptos y permisos

  • Proyecto: agrupa instancias y contenedores (normalmente uno por cliente). Tiene color, etiquetas (para filtrar en «Proyectos») y, opcionalmente, un cliente y el «Modo test» para demos.
  • Cuotas (solo las ponen los administradores, al editar el proyecto): máximo de instancias y de RAM reservada (la suma de los límites de memoria de sus instancias). Se comprueban al crear, duplicar, mover, crear desde backup, pedir una demo y subir un límite de memoria. Metrics → Uso por proyecto muestra lo que ocupa cada uno frente a su cuota (también en CSV, para facturar) y el día 1 de cada mes llega el resumen por email.
  • Instancia: un Odoo (versiones 8 a 20) con su propio PostgreSQL, su filestore, su red y su dirección. Se muestra como proyecto / instancia.
  • Tarea: todo lo que tarda (desplegar, respaldar, restaurar, duplicar, instalar módulos, limpiar…) lo ejecuta un worker en segundo plano, de una en una, con su log y barra de progreso (ver Tareas y Actividad).

Quién puede hacer qué

  • Administrador (superusuario): todo, incluidos Usuarios, Docker, Configuración global (dominio, respaldos, IA, email, demos) y la limpieza de Docker.
  • Usuario: crea y gestiona sus proyectos e instancias.
  • Cliente (casilla «Cliente» del usuario, asignado a un proyecto): ve sus proyectos y hace lo que el proyecto le permita en Permisos del cliente (al editarlo): desplegar, reiniciar y detener; crear y descargar backups; ver los logs (las tres, sí por defecto); restaurar sus backups y entrar como admin en Odoo (no por defecto). Nunca cambia código ni configuración, no ve la Master Password ni la contraseña del administrador, ni las pestañas Console, Domains, Modules y Migrar. Todo lo que hace queda en la Auditoría. Las mismas reglas valen en la API y el MCP.

2. Crear una instancia

  1. Dashboard o Proyecto → Nueva instancia.
  2. Elige proyecto, nombre, versión de Odoo y, si tienes código propio, el repositorio de GitHub (HTTPS) y la rama. Para repositorios privados necesitas tu token en Configuración → GitHub.
  3. Opcional: nombre de la base de datos (vacío = auto-detección), «Base por defecto de las demos» (varias bases en una instancia, Odoo 18+) y dominio propio.
  4. Al guardar se crea una rama con el nombre de la instancia en tu repositorio (si hay token) y se pone en cola el despliegue.

Qué hace el despliegue

  • Clona o actualiza el repositorio principal y los repositorios extra, descarga la imagen de Odoo (las versiones antiguas se emulan en servidores ARM) y el PostgreSQL adecuado a la versión.
  • Crea los contenedores odoo_<nombre> y db_<nombre>, su red y su volumen de datos, escribe odoo.conf (Master Password, proxy_mode) y publica la ruta en Traefik.
  • La instancia queda en https://cliente-versión-nombre.tudominio con su certificado de Let's Encrypt.
  • Al terminar bien, se pone en cola una limpieza automática de Docker.

Otras formas de crear una instancia

  • Duplicar una instancia: copia la base de datos, el filestore, los repositorios y las variables de entorno. Por defecto la copia se neutraliza antes de arrancar: correo entrante y saliente, tareas programadas (salvo la limpieza automática), métodos de pago y claves API desactivados y UUID de la base nuevo (en Odoo 16+ se ve la cinta «neutralizada»). Desmarca «Neutralizar la copia» (o envía neutralize: false por la API) solo si la copia va a sustituir a la original.
  • Refrescar una staging: en la pestaña Backups de la copia, «Refrescar datos desde otra instancia» sustituye sus bases de datos y adjuntos por los de otra de la misma versión (por defecto, su original) sin tocar su código, rama ni configuración, y la neutraliza (recomendado). Hay que escribir su nombre para confirmar; queda en la Auditoría.
  • Desde un backup: Backups → «Importar un backup y crear una instancia» (detecta la versión y la base).
  • Por la API o el MCP: crear una instancia también la despliega (ver API y MCP).
  • Demos del «Modo test» (ver Demos).

La base de datos de Odoo no se crea sola: créala en la ficha de la instancia (Information → Crear base de datos: nombre, idioma y datos de demo) o por la API (create-database); las dos guardan el usuario y la contraseña del administrador. En las instancias nuevas el gestor de Odoo (/web/database/manager) está cerrado; ábrelo en Information solo si lo necesitas.

3. Gestionar una instancia

La ficha tiene las pestañas Information, Logs, Console, Domains, Modules, Backups, Migrar, IA y Tareas recientes.

  • Deploy: vuelve a desplegar (recrea los contenedores con la configuración actual; los datos se conservan).
  • Restart / Stop: reiniciar arranca antes la base de datos si estaba parada. Una instancia parada pierde su ruta en Traefik (no gasta certificados) y la recupera al reiniciarla. Tras reiniciar el servidor, las instancias vuelven solas salvo las que paraste tú.
  • Renombrar (mueve contenedores y volúmenes), Mover a otro de tus proyectos (la dirección no cambia) y Eliminar (borra contenedores, volúmenes, workspace, rutas y sus backups).
  • Límite de memoria (Information, 1536 MB por defecto): tope de RAM del contenedor de Odoo para que una instancia no deje sin memoria al servidor ni a las demás. Se aplica en marcha, sin reiniciar (el worker lo revisa cada minuto); 0 = sin límite, en el próximo despliegue. Si Odoo lo alcanza, el sistema corta el proceso y Docker lo vuelve a arrancar: súbelo si una instancia se reinicia sola.
  • Ahorro de memoria (Information, desactivado salvo que lo elijas): «Detener si nadie entra en N días» (3, 7, 14 o 30; mira el registro de entradas de su Odoo, avisa el día antes y al detenerla) y un horario diario en UTC para arrancarla y detenerla. Pensado para instancias de prueba.
  • Descripción (demos): texto que acompaña a la instancia en la página de demos de su proyecto.
  • Logs de Odoo y Console para ejecutar comandos en el contenedor.

4. Acceso a Odoo: admin y contraseñas

  • Entrar como admin (icono de llave, en la ficha, la lista de instancias y el proyecto): abre Odoo como administrador sin contraseña con un enlace firmado de un solo uso válido 60 segundos. En Odoo 10 y 11 entra con un usuario propio del panel («Administrador (Community SH)»).
  • Master Password: la del gestor de bases de datos de Odoo (/web/database/manager). Se ve y se copia en Information; se aplica al redesplegar.
  • Gestor de bases de datos de Odoo (Information): cerrado por defecto en las instancias nuevas (las que ya existían siguen abiertas hasta que lo cierres). Cerrado, /web/database/* y el servicio XML-RPC db responden 403 en sus dominios al momento y, al redesplegar, Odoo también rechaza crear, copiar, descargar, restaurar o borrar bases (list_db = False), también por el puerto directo. Con varias bases de datos se entra con ?db=nombre. Abrirlo o cerrarlo queda en la Auditoría.
  • Administrador (Information): usuario y contraseña del administrador de Odoo, con botones para mostrar y copiar, para compartirlos. Aparece cuando la contraseña la puso la plataforma (base creada por la API/MCP, demos, copias).
  • Restablecer contraseña (en el bloque Administrador): pone una contraseña nueva al administrador (la que escribas, 8-64 letras, números, «_» o «-», o una aleatoria si lo dejas vacío) en la base de la instancia, o en todas si no tiene una fija, y la guarda en la ficha. Sirve también si la base se creó fuera de la plataforma. La anterior deja de funcionar y se cierran sus sesiones. La instancia tiene que estar desplegada. También por la API (POST /api/instances/{id}/reset-admin-password/) y el MCP (reset_admin_password), que devuelven la contraseña al momento; get_instance del MCP muestra el administrador a quien gestiona la instancia.

Si cambias la contraseña del administrador dentro de Odoo, la que muestra el panel deja de valer: restablécela desde el panel para volver a tenerla.

5. Código, módulos y configuración (pestaña Modules)

  • Repositorios extra (OCA, odoo/enterprise…): URL HTTPS y rama; se clonan y se añaden al addons_path en el próximo despliegue. Los privados usan el token de GitHub del dueño.
  • Pull: trae los últimos commits del repositorio principal y de los extra y reinicia Odoo, sin redesplegar.
  • Actualización automática (activada por defecto, «Pull y reiniciar Odoo»; también «Pull y actualizar todos los módulos (-u all)» o Desactivada):
    • Un push a la rama de cualquiera de sus repositorios actualiza todas las instancias en marcha que usan ese repositorio y rama (basta un webhook por repositorio). Botón «Crear webhook en GitHub» o URL y secreto para añadirlo a mano.
    • Además, cada día desde las 02:00 UTC el worker hace pull de todas ellas. Solo se reinicia Odoo (o se hace -u all) si cambió algún commit o la configuración.
  • Instalar un módulo por su nombre técnico (o «Instalar el tema Community SH») en todas las bases, con opción de actualizar (-u). Si falla, la base queda como estaba.
  • Instalar desde requirements.txt: pip instala los paquetes en el volumen de datos, así se conservan al redesplegar.
  • Variables de entorno del contenedor de Odoo (NOMBRE=valor, una por línea): se aplican en cada despliegue; solo se ven sus nombres. Las copias las heredan; las demos no.
  • Navegador (WhatsApp Web): instala Google Chrome en el contenedor de Odoo y lo reinstala en cada despliegue.

6. Dominios y HTTPS (pestaña Domains)

  • Cada instancia tiene su subdominio cliente-versión-nombre.tudominio, cubierto por un único registro DNS *.tudominio. Traefik emite y renueva los certificados.
  • Dominio propio: apunta su DNS (registro A) a la IP del servidor y configúralo en la pestaña; no puede tomar el subdominio de otra instancia o contenedor.
  • Si falta el certificado, la ficha avisa y explica por qué (DNS que no apunta, límite de Let's Encrypt…). Let's Encrypt permite 50 certificados por semana por dominio.
  • El dominio principal del panel se configura en Configuración → Domain & SSL.

7. Backups y restauraciones

  • Crear backup (pestaña Backups): base de datos y, si quieres, filestore. Con varias bases se guarda una copia de cada una.
  • Backups automáticos: Configuración → Respaldos (activar, frecuencia y cuántas copias conservar por instancia). Si alguno falla, llega una alerta.
  • Copia fuera del servidor (S3): en Configuración → Respaldos, con un bucket compatible con S3 (AWS S3, Backblaze B2, Cloudflare R2, Wasabi, MinIO…), cada backup se sube también allí como tarea propia («Copiar backup fuera (S3)»), queda marcado con ☁ S3 y las copias más antiguas que los días indicados se borran del bucket. «Probar conexión» comprueba que se puede escribir sin guardar nada. Para recuperar uno: en la pestaña Backups de la instancia, Copias en S3 → Ver copias → Restaurar (se descarga y se restaura como tarea).
  • Comprobación de backups: cada semana (o con «Comprobar backups ahora» en Configuración → Respaldos) se revisa el último backup de cada instancia: que el ZIP está entero, que lleva un volcado de PostgreSQL válido y que la copia en S3 mide lo mismo. Si algo falla, llega una alerta.
  • El propio panel: con el bucket configurado, cada día la tarea «Copia del panel fuera (S3)» sube a _panel/ una copia de la base de datos del panel (proyectos, usuarios, configuración…) y de los certificados (acme.json). El .env no se sube a propósito: guarda la clave que descifra los secretos; consérvalo aparte (por ejemplo, en un gestor de contraseñas), porque sin él una copia de la base no sirve para recuperar las claves.
  • Restaurar un backup sobre la instancia (detiene Odoo y cierra sus conexiones antes de recrear la base) o «Restaurar desde un archivo».
  • Importar: además de los backups del panel, acepta los del gestor de Odoo (.zip con dump.sql y filestore) y volcados .dump.
  • Menú Backups: todos los respaldos, descargar e «Importar un backup y crear una instancia».

8. Demos (Modo test)

  1. En el proyecto marca Modo test: URL de la página de demos (p. ej. /bim), días de prueba (15), proyecto hermano donde se crean, texto para el visitante y demos a la vez.
  2. El visitante abre la página pública, elige versión entre las instancias en marcha del proyecto (con su descripción), deja sus datos y resuelve el captcha.
  3. Se crea una copia en el proyecto hermano, neutralizada antes de arrancar (sus tareas programadas siguen activas): sin correo saliente, sin claves API, con contraseñas desconocidas para los demás usuarios y una contraseña nueva para el administrador. La página muestra el progreso y al final la dirección, el usuario y la contraseña, que también se envían por email si hay SMTP.
  4. Al vencer se detiene y 7 días después se elimina.
  • Límites: una demo por email al mes, 3 al mes por conexión, un máximo diario y un máximo de demos a la vez en el servidor (Configuración → Demos). No se crea si falta memoria.
  • Tu web puede pedir demos sin captcha con la clave de API del proyecto (tarjeta «Modo test» → Generar clave).
  • Quien pide una demo entra en Contactos, en la etapa «Demo».

9. Contactos (CRM)

  • Un contacto por email, con sus datos, sus demos y notas propias; se conserva aunque la demo se elimine.
  • Tablero Kanban: Contactado, Demo, Propuesta, A la espera, Ganado y Perdido (arrastra las tarjetas). También vista de lista, búsqueda, filtros, alta manual y exportar a CSV.

10. IA y migraciones

  • Asistente de IA (pestaña IA, con la IA configurada en Configuración → IA): crea y modifica módulos en los addons de la instancia y los instala. Admite adjuntos, etiquetar módulos con @, muestra un plan paso a paso y cada respuesta que cambió archivos tiene «Deshacer estos cambios».
  • /ia desde Odoo: escribe /ia … en el chatter de cualquier registro y la respuesta llega a ese chatter.
  • Migrar (pestaña Migrar): trae datos de otro Odoo 8+ por XML-RPC a instancias 14+ (contactos, productos, ventas, compras, facturas y pagos); se puede repetir sin duplicar.

11. Contenedores (apps)

  • Menú Contenedores o Proyecto → «Nuevo contenedor»: apps a partir de plantillas (p. ej. ERPSqlite) o construidas desde un repositorio y un Dockerfile.
  • Las construcciones van en su propio worker (no frenan despliegues ni backups). Cada contenedor tiene https://nombre.tudominio; parado deja de tener ruta.

12. Docker y limpieza de disco

  • Limpieza automática: cada vez que se crea bien una instancia (formulario, API/MCP, duplicar, desde backup o demo) se pone en cola una limpieza de lo que Docker no usa: contenedores detenidos que no son de ninguna instancia, imágenes sin etiqueta y sin usar, caché de build y redes sin uso. Una sola en cola aunque se creen varias seguidas; si se está construyendo un contenedor, se omite.
  • Botón «Limpiar» del Dashboard (administradores): lanza esa misma limpieza cuando quieras.
  • Docker → Limpieza: muestra qué y cuánto se libera y deja elegir; los volúmenes sin uso solo se borran aquí, escribiendo BORRAR.
  • Nunca se tocan el panel, las instancias (aunque estén paradas), sus filestores, bases y redes, ni los contenedores del panel y sus volúmenes. Una imagen borrada se vuelve a descargar en el próximo despliegue que la necesite.
  • Los logs de cada contenedor (Odoo, PostgreSQL, apps y el propio panel) tienen un tope de 20 MB × 3 ficheros, para que un error en bucle no llene el disco. En los contenedores que ya existían se aplica al volver a crearlos (al redesplegar).
  • El servidor tiene memoria limitada: detén las instancias de prueba cuando acabes.

13. Tareas y Actividad

  • Cada tarea guarda su log completo con la hora y una barra de progreso que avanza en directo, en la pestaña «Tareas recientes» de la instancia y en el menú Actividad (filtros por estado, tipo e instancia).
  • Estados: En cola, En curso, Completada y Fallida (con el error). Si el worker se reinicia a mitad, la tarea queda como fallida.

Disponibilidad y alertas

  • Cada 5 minutos el worker pide la página de login de cada instancia en marcha (salvo las que tienen una tarea en curso). Tras dos fallos seguidos la marca como No responde (en la lista y en Information, con el motivo); si contesta, muestra el tiempo de respuesta.
  • Alertas (Configuración → General): cuando falla una tarea, una instancia deja de responder o vuelve, el disco pasa del 90 %, la memoria lleva 5 minutos por encima del 90 % o falta el certificado HTTPS de una instancia (se revisa cada hora). Van por email a los «Emails para notificaciones» (o a los administradores) con el servidor de Configuración → Email, y opcionalmente a un webhook (Slack, Discord, Google Chat, n8n…). La misma alerta no se repite en 6 horas (la de certificado, en 24).

14. Dashboard, Metrics y Todo

  • Dashboard: las cifras principales, cada una enlazada a su página; CPU, memoria y disco en verde (<50 %), naranja (50-90 %) o rojo (>90 %). Al pulsar CPU, Memoria o Disco se abre el uso por instancia ordenado por ese recurso: qué instancia consume qué.
  • Metrics: uso de CPU y RAM en las últimas 24 horas, 7 días, 30 días y 12 meses. En Recursos, el uso por instancia: CPU y RAM de su Odoo y su PostgreSQL ahora (con cuánto de su límite gasta) y disco de sus datos (base de datos y adjuntos), su código y sus backups, también de las instancias paradas; se ordena pulsando las cabeceras. El disco se mide cada 10 minutos o con «Medir el disco ahora». Debajo, el uso por contenedor.
  • En la ficha de cada instancia, Information muestra su uso ahora (CPU y RAM de Odoo y PostgreSQL).
  • Todo: tareas del equipo (por hacer, en curso, completadas) con nota de lo realizado.

15. API y MCP (Claude)

  • API REST (Configuración → API → Generar token; Authorization: Bearer …): proyectos, instancias (crear y desplegar, reiniciar, detener, backup, duplicar, variables de entorno, repositorios extra, create-database, install-module), backups, tareas con su log, contenedores, contactos, Todo y demos.
  • Para una IA: Configuración → API → «Generar token y descargar .md» crea un token nuevo y descarga community-sh-api.md con el token, la URL base y toda la documentación (endpoints, tareas, errores, ejemplos y, si está activo, cómo conectar el MCP). Pásaselo a Claude, ChatGPT… para que use la API por ti. Guárdalo como una contraseña; el token se revoca en «Tus tokens».
  • MCP (Configuración → MCP): conecta Claude con /mcp/ y un token personal; actúa con los permisos de su usuario.
  • Los tokens se muestran una sola vez y exigen 2FA cuando es obligatorio.
  • Las contraseñas que recibe una tarea (crear una base de datos, restablecer la del administrador) nunca se devuelven al consultar tareas (salen como ••••••) y se borran de la tarea al terminar; la del administrador queda en la ficha de la instancia.

16. Usuarios, seguridad y configuración

  • Usuarios (administradores): crear, editar y marcar como Cliente.
  • Auditoría (administradores, en el menú): quién hizo qué y desde qué IP: inicios de sesión (también los fallidos), cada vez que alguien muestra o copia la Master Password o la contraseña del administrador, «Entrar como admin», restablecer contraseñas, cambios de configuración, tokens creados y revocados, usuarios y cambios en instancias (eliminar, renombrar, mover, memoria, variables de entorno). Las contraseñas ya no van dentro de la página: se piden al servidor al pulsar mostrar o copiar.
  • Claves cifradas: el token de GitHub, la clave de OpenAI, la contraseña SMTP, la secret key de S3 y, en cada instancia, la Master Password, la contraseña del administrador, el secreto del webhook y las variables de entorno se guardan cifrados en la base de datos; una copia de la base sola no los revela. La clave es FIELD_ENCRYPTION_KEY del .env o, si no está, una derivada de DJANGO_SECRET_KEY: no cambies ninguna de las dos sin descifrar antes, o esos valores dejarán de poder leerse.
  • 2FA desde tu perfil; desactivarlo o cambiarlo pide un código actual. El acceso se bloquea tras varios intentos fallidos.
  • Configuración: GitHub (token para repos privados; la pestaña Ayuda explica cómo crearlo), Domain & SSL, General, Respaldos, IA, Email (SMTP con «Enviar prueba»), Demos, MCP y API.

17. Seguridad del servidor

  • Docker filtrado para la web: el contenedor web del panel ya no tiene el socket de Docker (que equivale a ser root en el servidor). Habla con Docker a través del servicio docker-proxy, que deja pasar lo que hace el panel (logs, consola y pip, arrancar, parar y reiniciar, la página Docker, crear contenedores de apps) y rechaza lo que daría el servidor: contenedores privilegiados, con capacidades extra o con los espacios del host, montar carpetas del host fuera de instances/, el socket de Docker, entrar, copiar archivos o borrar los contenedores del propio panel, sus volúmenes y su red interna. Los despliegues, backups y demás tareas siguen en los workers.
  • Un contenedor de apps que necesite otra carpeta del host (solo administradores): añádela a DOCKER_PROXY_ALLOWED_BINDS en el .env (separadas por comas) y redespliega. Montar el socket de Docker (p. ej. Portainer) ya no se puede desde la web.
  • Código de solo lectura: el contenedor web monta el código sin permiso de escritura (solo escribe en media, backups, instances, letsencrypt, traefik, staticfiles y ai_attachments), así que un fallo en una página no puede cambiar el código que ejecutan los workers. En instalaciones con SQLite queda escribible (PANEL_CODE_MOUNT=rw).
  • Gestor de bases de datos de Odoo: cerrado por defecto (ver Acceso a Odoo); así una Master Password filtrada no basta para descargar o borrar la base desde internet.
  • Sin scripts de terceros: Alpine.js, Lucide, Tailwind y Chart.js se sirven desde el propio panel (static/vendor, versiones fijas comprobadas contra npm), no desde CDNs. Si un CDN fuese comprometido, no podría ejecutar código en el panel con tu sesión.
  • Content-Security-Policy: el navegador solo ejecuta scripts del panel, solo le habla al panel (no puede mandar datos a otro sitio), no carga plugins ni deja meter el panel en un iframe. Las fuentes de Google y las imágenes por HTTPS siguen permitidas.
  • Puerto 8000: con un dominio, el panel solo se sirve por Traefik (HTTPS). El despliegue añade PANEL_BIND=127.0.0.1 al .env si falta, así el puerto 8000 en HTTP plano no queda abierto a internet.

18. Actualizaciones del panel

  • Cada cambio del panel sube la versión y se documenta en Acerca de y en esta Ayuda.
  • Un push a la rama principal pasa los tests en GitHub Actions (con PostgreSQL 16, el mismo motor que producción) y, si van bien, se despliega en el servidor: espera a las tareas en curso, guarda una copia de la base del panel, libera espacio si quedan menos de 5 GB, construye y, tras arrancar, abre las páginas principales como administrador (manage.py smoke_check). Si el build falla, el panel no responde o alguna página da error, vuelve a la versión anterior.
